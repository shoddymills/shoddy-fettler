Shoddy · Picker

Guardrails

The second level. You name the databases, and the picker grades what is in them: which tables answer, which verbs they allow, and which columns are not there at all.

← PreviousToolsScreeningsNext →

This page describes the guardrails level. It is off until .picker.json has a guardrails section. With it off, pick opens every database the login can reach, as Tools shows. With it on, only the databases you declare exist, and a scope can narrow what a table allows or hide some of its columns.

Guardrails add to the tools level. They do not replace it. The query gate, the caps and the five verbs stay the same, and the tools section still holds each server and its connection.

A guardrails file, and what it gives you

Add a guardrails section beside tools, listing the databases on each server. Here is one database with two scopes, beside the answer pick catalogs gives for it.

.picker.json

{
  "tools": {
    "servers": {
      "main": { "connect": "env:MAIN_SQL" }
    }
  },
  "guardrails": {
    "servers": {
      "main": {
        "databases": {
          "Sales": {
            "can": ["list", "select", "describe"],
            "scopes": [
              { "object": "dbo.Customers",
                "can": ["list", "select"],
                "columns": ["-ssn", "-dob"] },
              { "object": "audit.*", "can": [] }
            ]
          }
        }
      }
    }
  }
}

pick catalogs

levels
  tools       on, always; settings from C:\github\app\.picker.json
  guardrails  on, from C:\github\app\.picker.json
  screenings  off

main  (connect: env:MAIN_SQL)
  Sales: list select describe
    dbo.Customers: list select  columns: -dob -ssn
    audit.*: nothing
source: C:\github\app\.picker.json
  • The guardrails line now says on, and names the file that turned it on.
  • The server no longer says "every database this login can reach". It lists Sales, because Sales is now the only database there is.
  • Each scope shows on its own line, with its verbs and its column rule. The word nothing means the scope allows no verb at all.

Three rules about where things go:

  • A server under guardrails must also be under tools. Otherwise the file is refused, and the message says to declare the server under tools with its connect.
  • A connect under guardrails is refused, because a connection belongs to the tools level.
  • With guardrails on, a server the section does not list has no databases. Guardrails apply to every server in the file, so declare what each one should show.

Declared databases: the whole list

A database the file does not declare does not exist. pick does not say that it is hidden, and answers in the same words as for a table that was never there.

$ pick select "SELECT * FROM Finance.dbo.Ledger"
pick: there is no table or view called 'Finance.dbo.Ledger' in the declared databases. Run objects to list what is here (Finance.dbo.Ledger)
$ pick select "SELECT * FROM Sales.dbo.NoSuchTable"
pick: there is no table or view called 'Sales.dbo.NoSuchTable' in the declared databases. Run objects to list what is here (Sales.dbo.NoSuchTable)

The two refusals match on purpose. If they differed, a caller could map the server by reading refusals. This rule is called hidden is absent, and it holds for databases, tables and columns alike.

  • There is no default database. A short name such as Customers is looked for in the declared databases only. The connection's own database is never asked.
  • A short name found in two declared databases is refused, naming both, and the fix is to write the full name. Every declared database takes part in that search, so declare only what you use.
  • One statement reaches one server. A query may join declared databases on the same server, but not on two servers.
  • The same database name on two servers cannot be told apart, so naming it is refused. Declare it on one server, and reach the other through its own .picker.json, using --config PATH.

What a database allows

can lists the verbs a database allows. There are three grant words, and each one lets a caller do one thing with a table.

WordLets a caller
listsee the table in objects, and learn that it exists
selectread its rows with select
describeread its columns, indexes and keys with describe
  • Without list, a table is absent. It is missing from objects, and a query that names it is refused as not there, with exit code 3.
  • Listed but without select, a table is refused plainly, with exit code 8. The refusal names what the table does allow, because the listing already showed that it exists.
  • A misspelt word refuses the whole file, and the message names the three words. Otherwise "selct" would take a verb away without anyone noticing.

Scopes replace. The most specific wins

A scope sets the rules for some of the tables in a database. It names an object pattern, schema.object, where * stands for a whole part. For example, audit.* matches every table in the audit schema.

A scope replaces the database's rules for the tables it matches, and does not add to them. An exact table name beats a whole schema. A table that matches no scope gets the database's own can.

  • A scope must state its can. A scope with no can is refused, because silence could mean either "allow nothing" or "allow what the database allows".
  • "can": [] hides the tables it matches. That is how audit.* above seals a whole schema.
  • A scope's screen is not set here. Screens go under screenings, keyed by the database and the scope's pattern, as Screenings shows.

Hidden columns

columns on a scope decides which columns exist for the caller. There are three ways to write it, and one that is refused.

You writeThe caller sees
"columns": true, or nothingevery column
"columns": ["name", "city"]only those columns
"columns": ["-ssn", "-dob"]every column except those
"columns": ["name", "-ssn"]refused when the file is read. One list cannot both include and exclude

A hidden column does not exist anywhere. It is refused in the select list, in WHERE, ON, GROUP BY and ORDER BY, and inside expressions. A filter such as WHERE ssn = … would let a caller guess a column one row at a time, so it is refused too.

$ pick select "SELECT name FROM Sales.dbo.Customers WHERE ssn = '123-45-6789'"
pick: 'ssn' is not a column of Sales.dbo.Customers. Run describe to see its columns (ssn)
  • The refusal is the one for a column that does not exist, and it never says "hidden".
  • SELECT * is not a way round it. The star becomes the allowed columns before the server sees the query, and the answer shows the list it chose.
  • describe leaves hidden columns out. An index or key that uses a hidden column is left out whole, because a note saying "one column not shown" would tell the caller the column exists.

More than one database, more than one server

servers and databases are both plural. A staging database beside a warehouse, and a second server beside the first, fit in one file like this.

{
  "tools": {
    "servers": {
      "warehouse": { "connect": "env:WAREHOUSE_SQL" },
      "ops":       { "connect": "env:OPS_SQL" }
    }
  },
  "guardrails": {
    "servers": {
      "warehouse": {
        "databases": {
          "Staging": { "can": ["list", "select", "describe"] },
          "Sales":   { "can": ["list", "select", "describe"] }
        }
      },
      "ops": {
        "databases": {
          "Orders": { "can": ["list", "describe"] }
        }
      }
    }
  }
}
  • A query may join databases on one server. SELECT … FROM Staging.load.Batch b JOIN Sales.dbo.Orders o ON … is one statement on one connection. Each table keeps its own scope and column rule.
  • A query that reaches two servers is refused, naming both, so run two selects instead. pick returns what a server produced, and does not build a joined answer that no server made.
  • Each server has its own connect, and should have its own narrow login. The next two sections cover both.

The local file

.picker.local.json sits beside .picker.json, and you keep it out of source control. It holds the facts that belong to one machine: connection strings, and where the screening models are. It may hold those two things and nothing else.

{
  "tools": {
    "servers": {
      "main": {
        "connect": "Server=db.internal;Integrated Security=true;TrustServerCertificate=true"
      }
    }
  },
  "screenings": { "models": "C:/models/screening" }
}
  • The local file may supply tools.servers.NAME.connect and screenings.models. Anything else in it refuses the load.
  • It cannot add to what is declared. A server named only in the local file is refused, and so is a guardrails section, a databases entry or a screen. Each would be a rule that nobody reviewed.
  • If both files give a connect, the local one wins. Pick one place per server, so that the next reader is not left guessing.
  • pick reads both files again before every call, so an edit takes effect on the next call with no restart.

Who can write these two files

Whoever can write these two files decides what pick allows. The next call obeys any edit, because pick reads them every time. pick itself cannot write them, because it has no write verb, but another tool the assistant holds probably can.

  • If the machine also runs fettle, the files are already protected. fettle refuses to write .picker.json and .picker.local.json, just as it refuses to write its own configuration.
  • If it does not, set both files read-only, so that an assistant's file tools cannot rewrite them by accident.
Windows · PowerShell
Set-ItemProperty .picker.json, .picker.local.json -Name IsReadOnly -Value $true
macOS and Linux
chmod a-w .picker.json .picker.local.json

Note Read-only slows a tool down. It does not stop one. A tool that can run a shell can clear the setting with one command, so denying the shell is the stronger protection.

Connect as a login that could not do more

Connect as a login granted only SELECT and VIEW DEFINITION on the declared databases. pick enforces its rules inside pick, but the server has rules of its own, and the two should agree. Then even a fault in pick has nothing wider to use.

Declaring a database grants the login nothing. If the login cannot enter a declared database, the server says so, and pick reports that as denied, exit code 9, meaning the server declined. It never reports it as refused, which means pick declined, so nobody debugs a boundary that is working.

A SQL login is one way to do this. It is not required. Most teams connect with integrated security (Integrated Security=true), where the connection arrives as a Windows or Entra account with no password anywhere. Grant the same two rights to that account, to a group, or to a role the account belongs to. Only the name in the T-SQL changes.

An administrator runs the grant once, and it is all that pick's login can ever do. With a SQL login of its own, it looks like this:

CREATE LOGIN pick_reader WITH PASSWORD = 'a-strong-generated-password';
USE Sales;
CREATE USER pick_reader FOR LOGIN pick_reader;
GRANT SELECT          TO pick_reader;   -- the rows
GRANT VIEW DEFINITION TO pick_reader;   -- the metadata describe reads

With integrated security, the same two grants go to the account or its group. Or they go to a role, so that membership is the only thing that ever changes:

CREATE LOGIN [DOMAIN\report-readers] FROM WINDOWS;  -- a group: membership stays AD's job
USE Sales;
CREATE USER [DOMAIN\report-readers] FOR LOGIN [DOMAIN\report-readers];
CREATE ROLE pick_reading;
GRANT SELECT, VIEW DEFINITION TO pick_reading;
ALTER ROLE pick_reading ADD MEMBER [DOMAIN\report-readers];

On a development machine with LocalDB, integrated security covers all of this, because the instance is yours alone. On a shared server, the grants are the whole task. A SQL login's password goes in the local file or an environment variable, never in the checked-in file.

How the boundary is held

  • The assistant needs nothing new denied. Its built-in tools work on files and shells, and none of them speaks SQL, so registering pick is one entry in the client's settings.
  • pick's boundary is a file it reads before every call. No verb takes a connection string or a database name, so no call can widen it, and pick has no write verb at all.
  • The server's boundary is the declared databases. There is no default database, no USE, no sys.* and no linked server. The reference holds every refusal.
  • Under all of it is the login, granted only SELECT and VIEW DEFINITION, so the server keeps a boundary of its own.

Check the wiring

$ pick doctor
pick X.Y.Z
  ok tools: on, always; settings from C:\github\app\.picker.json
  ok guardrails: on, from C:\github\app\.picker.json
  ok screenings: off
  ok configuration: C:\github\app\.picker.json
  ok server main: connects (1 database(s) declared)

doctor never prints a connection string. It says whether the server answered, not how pick reached it. Then run pick catalogs to see what is declared, and pick objects to see what a caller may list.

Verifying the boundary

Prove it. Do not trust it. A correct file and a boundary that holds are two different claims, and only the second one matters. Try each of these yourself, or ask the assistant to, and check what comes back.

Try to…A correct setup…
select from a database the file does not declarerefuses with exit 3, in the words for a table that never existed, whether or not the database is real
select from a table whose scope is "can": []refuses with exit 3, and objects never listed it
select from a table that allows list but not selectrefuses with exit 8, naming what the table does allow
select a column the scope hides, then filter on it with WHERErefuses both with exit 3, in the words for a column that does not exist
SELECT * from that same tablereturns every column except the hidden ones, and names the columns it chose
run DELETE, EXEC, or a second statementrefuses with exit 8, each with its own reason
read sys.tables, or call OBJECT_DEFINITION()refuses with exit 8. The catalog answers through describe, under the scopes
describe a viewgives its columns and never its stored text
connect with the login and a plain SQL client, and try an INSERTthe server refuses. The login's grant stops at SELECT
edit .picker.json, then call again without restartingthe change applies, because pick reads the file before every call
