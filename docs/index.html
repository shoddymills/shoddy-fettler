Shoddy · Fettler

Fettler & Picker

Bounded tools for an AI assistant and for scripts. Files through fettle, SQL Server through pick. Each is one program with two front ends, and neither one uses a shell.

Fettle, for the filesNext →

fettle: the files

Find, search, read and edit files, with answers a script or an assistant can hand straight back. A batch of edits lands whole or not at all. With no configuration, the folder you start in is the one tree. Turn on guardrails to declare the trees and what each allows. Turn on screenings to refuse regulated data.

Start with the files →

pick: the SQL Server

SELECT and DESCRIBE, one checked statement at a time. There is no default database, no USE, and no system catalog. A parser refuses anything it cannot check. Turn on guardrails to declare the databases, tables and columns that exist. The same screen covers the rows that come out.

Three levels

Both programs do three kinds of work, called levels. You turn a level on by writing a section of that name in the program's configuration file. The tools level is always on.

LevelOn whenWhat it gives you
toolsalways, with no filethe operations themselves: search, read, edit and batch for files; SELECT and DESCRIBE through the query gate for data
guardrailsthe file has a guardrails sectiona declared list of trees or databases, what may be done in each, and nothing else existing
screeningsthe file has a screenings sectionthe screen that refuses to disclose regulated data

One set of rules, used twice

The two programs apply one set of rules to two kinds of data. Every rule below holds for both.

  • With guardrails on, the world is a declared list. fettle works in the trees listed in .fettler.json. pick works in the databases listed in .picker.json. Whatever a file does not name does not exist.
  • Hidden means absent. A path outside the trees, a hidden folder, an undeclared database and a hidden column are all refused in the same words as something that was never there. A refusal cannot be used to map what it protects.
  • No shell, anywhere. fettle runs only declared tasks, whole and without arguments. pick runs only one parsed and rewritten SELECT. Neither builds a command line.
  • A person writes the rules. The tools refuse to write their own configuration files, whatever permissions they hold.
  • Two front ends, one behaviour. Each program is a command-line tool for scripts and an MCP server for an assistant. MCP is the Model Context Protocol, the standard way an assistant launches a tool and talks to it. Both front ends use the same core, and the MCP answers are byte for byte the same as the command line's --json output. Where the two programs share an outcome word, they share the exit code too.

They can refuse to disclose regulated data

The screen is the screenings level: optional, off by default, and shared by both programs. A tree or a database can declare that certain things must not leave it. The first tier runs inside the program with nothing installed. It catches labelled record numbers, dates of birth, social security numbers, valid card numbers, email addresses and phone numbers.

"screenings": {
  "screen": { "records": ["identifiers"] }
}

When the screen finds something, it refuses the whole response: a file read, a search, or a set of rows. It never hands back a redacted copy, because a redacted copy looks safe and is not.

The screen does not catch names, addresses, conditions or free text on its own. Those need a model, which is a separate download. identifiers is the only category that works with nothing installed. clinical, legal and scientific screen nothing until you install a model, and the tools say so in plain words. See screenings for the files and screenings for the rows, each with its models. One set of models on disk serves both programs.
