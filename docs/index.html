Fettler & Picker

Bounded tools for a model and a script — the files through fettle, the SQL Server through pick. Two programs, two front ends each, and no shell between them and the data.

fettle — the files

Find, search, read and edit inside declared trees, and nothing else. No current directory, no path that climbs out, no shell to sneak past it. Batches land all or not at all, and a disclosure screen can refuse regulated data leaving a tree you name.

pick — the SQL Server

SELECT and DESCRIBE inside declared databases, and nothing else. No default database, no USE, no system catalog; tables, views and columns scoped one by one; one statement through a fail-closed parser gate — and the same screen over the rows coming out.

One discipline, twice

The two programs are one argument applied to two kinds of data, and every rule below holds for both:

  • The world is a declared list. A tree in .fettler.json; a database in .picker.json. Whatever the file does not name does not exist — there is no default directory and no default database to fall into.
  • Hidden is absent. A path outside the trees, a hidden scope, an undeclared database, an excluded column: each is refused in the same words as something that was never there, so a refusal cannot be used to map what it protects.
  • No shell, anywhere. fettle runs only declared tasks, whole and argumentless; pick runs only one parsed and rewritten SELECT. Neither ever composes a command line.
  • A person writes the rules, and the tools refuse to. The configuration files are refused by every write path of the very tools they govern.
  • Two front ends, one behaviour. Each program is a CLI for a script and an MCP server for a model over the same core, and the MCP answers are byte-identical to the CLI's --json mode. Where the outcome words match, the exit codes carry the same numbers in both programs.

They can refuse to disclose regulated data

Optional, off by default, and shared — one screen, both programs. A tree or a database can declare that certain things must not leave it. The first tier runs in process with nothing installed: labelled record numbers, dates of birth, SSNs, Luhn-valid cards, emails, phone numbers.

"trees": {
  "records": { "path": "./records", "can": ["list", "read"], "screen": ["identifiers"] }
}

Anything it finds refuses the whole response — a file read, a search, a result set of rows — rather than handing back a redacted copy that looks safe and is not.

And here is what it does not catch. Names, addresses, conditions and free text need a model, which is a separate download. identifiers is the only one of the four categories that works with nothing installed; clinical, legal and scientific screen nothing at all until you install one, and the tools say so in as many words rather than letting the category name imply otherwise. Screening for the files · screening for the rows · the models, for fettle and for pick — one installation on disk serves both.
