Fettler & Picker

Bounded tools for an AI assistant and for scripts. Files through fettle, SQL Server through pick. Each is one program with two front ends, and neither one uses a shell.

Fettle, for the filesNext →

fettle: the files

Find, search, read and edit files inside declared trees, and nothing else. A tree is a folder you name in a configuration file. There is no current directory, no path can climb out of a tree, and there is no shell. A batch of edits lands whole or not at all. A screen can refuse to send regulated data out of a tree you name.

pick: the SQL Server

SELECT and DESCRIBE inside declared databases, and nothing else. There is no default database, no USE, and no system catalog. Tables, views and columns are allowed one by one. One statement at a time passes through a parser that refuses anything it cannot check. The same screen covers the rows that come out.

One set of rules, used twice

The two programs apply one set of rules to two kinds of data. Every rule below holds for both.

  • The world is a declared list. fettle works in the trees listed in .fettler.json. pick works in the databases listed in .picker.json. Whatever a file does not name does not exist. There is no default directory and no default database.
  • Hidden means absent. A path outside the trees, a hidden folder, an undeclared database and a hidden column are all refused in the same words as something that was never there. A refusal cannot be used to map what it protects.
  • No shell, anywhere. fettle runs only declared tasks, whole and without arguments. pick runs only one parsed and rewritten SELECT. Neither builds a command line.
  • A person writes the rules. The tools refuse to write their own configuration files, whatever permissions they hold.
  • Two front ends, one behaviour. Each program is a command-line tool for scripts and an MCP server for an assistant. MCP is the Model Context Protocol, the standard way an assistant launches a tool and talks to it. Both front ends use the same core, and the MCP answers are byte for byte the same as the command line's --json output. Where the two programs share an outcome word, they share the exit code too.

They can refuse to disclose regulated data

The screen is optional, off by default, and shared by both programs. A tree or a database can declare that certain things must not leave it. The first tier runs inside the program with nothing installed. It catches labelled record numbers, dates of birth, social security numbers, valid card numbers, email addresses and phone numbers.

"trees": {
  "records": { "path": "./records", "can": ["list", "read"], "screen": ["identifiers"] }
}

When the screen finds something, it refuses the whole response: a file read, a search, or a set of rows. It never hands back a redacted copy, because a redacted copy looks safe and is not.

The screen does not catch names, addresses, conditions or free text on its own. Those need a model, which is a separate download. identifiers is the only category that works with nothing installed. clinical, legal and scientific screen nothing until you install a model, and the tools say so in plain words. See screening for the files, screening for the rows, and the models for fettle and for pick. One set of models on disk serves both programs.
