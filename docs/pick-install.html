Installing It

The download, getting it on PATH, the optional burler beside it, and the MCP front end for an assistant. Read this once per machine.

← PreviousQuick StartIn a ProjectNext →
This is the long way round, not the fastest route. If you just want pick working against a database, a handful of commands do it: the quick start. Come back here for the why and the detail.

Everything on this page is done once on a machine and not again. First, get the binary onto PATH. Then decide whether this machine screens with models — if so, burler sits beside pick. Then, optionally, register it with an assistant client. Turning it on against a particular server comes after; that is pick in a project.

The download

One download, one file on disk, no .NET runtime on the target machine. Every release attaches a self-contained, single-file pick per operating system, beside fettle's and burler's archives.

PlatformArchive
Windowspick-X.Y.Z-win-x64.zip
macOS, Apple siliconpick-X.Y.Z-osx-arm64.tar.gz
macOS, Intelpick-X.Y.Z-osx-x64.tar.gz
Linuxpick-X.Y.Z-linux-x64.tar.gz

The unix archives are tars because the execute bit only survives a tar. Each archive carries NOTICE and LICENSE. The single file has two Microsoft libraries bundled in — the ScriptDom T-SQL parser the query gate is built on, and the SqlClient driver that carries the connection — both MIT.

ScriptDom and SqlClient are in pick and in nothing else this project ships — just as PdfPig is in fettle alone and ONNX Runtime in burler alone. No program here references another; each carries its own allowlisted dependencies and nothing can leak between them. The full statement is in THIRD-PARTY-NOTICES.md.

Putting it on PATH

Windows · PowerShell
$dir = "$env:LOCALAPPDATA\Programs\pick"
New-Item -ItemType Directory -Force $dir | Out-Null
Expand-Archive pick-X.Y.Z-win-x64.zip -DestinationPath $dir -Force
Get-ChildItem $dir -Recurse | Unblock-File
$user = [Environment]::GetEnvironmentVariable('Path', 'User')
if ($user -notlike "*$dir*") {
    [Environment]::SetEnvironmentVariable('Path', "$user;$dir", 'User')
}
macOS and Linux
mkdir -p ~/.local/bin
tar -xzf pick-X.Y.Z-osx-arm64.tar.gz -C ~/.local/bin
xattr -d com.apple.quarantine ~/.local/bin/pick   # macOS only

Then open a new terminal — the one you just used still has the old PATH — and check it:

pick version

Three traps, all of them silent:

  • A stale terminal. A shell reads PATH once, when it starts, so the change is invisible to every terminal already open. Open a new one before deciding it did not work.
  • The Mark of the Web, on Windows. A downloaded archive carries a flag its contents inherit, and a flagged executable may be refused or interrogated every launch — Unblock-File clears it.
  • Quarantine, on macOS. The same idea by another name; xattr -d com.apple.quarantine clears it.

From source

Nothing else in this repository has to be built first. Picker references no other project here:

./scripts/fettler-build.ps1 publish X.Y.Z    # cuts fettle, burler AND pick archives

Archives land in artifacts/publish/. Or publish just pick for this machine:

dotnet publish pick -c Release -r win-x64 --self-contained `
    -p:PublishSingleFile=true -o $env:LOCALAPPDATA\Programs\pick

Every platform is first-class, by construction

SQL Server's client stack historically leaned on a native Windows networking layer — the piece that made "works on my machine" mean "works on Windows". pick pins the driver's managed networking path everywhere: once in the executable's runtime configuration, and once more as the first line of its Main, so no code path can run before the pin is set. The same code moves the bytes on Windows, macOS and Linux, and no native networking library ships in any archive. There is no Windows-only behaviour to fall back to, which means there is none to drift.

burler sits beside it — if you screen with models

The disclosure screen's first tier runs inside pick with nothing installed. The model-backed categories — clinical, legal, scientific — need burler, the same model host fettle uses. One download serves both programs, and one models directory serves both installs.

  • It is looked for beside the running executable, never on PATH: put burler (or burler.exe) in the same directory as pick. Already running it beside fettle? Copy the same file — the two installs may share a models directory but each program wants the sidecar beside itself.
  • The models are a separate download, laid out per category — the models page walks it checkpoint by checkpoint, licences included.
  • pick doctor reports both facts: the models directory the configuration names (and whether it exists), and whether burler is where it is expected — with the note that only model-backed screening needs it.

Registering the MCP server

pick has no setup verb — a person writes the registration. That is a smaller job than it is for fettle, because there is nothing else to write: no tree file to scaffold, no deny list to install, no instruction block. One JSON entry per project, and the boundary itself is the two .picker files, which you write anyway.

For Claude Code (and the VS Code extension, which shares its registry), in the project's .mcp.json:

{
  "mcpServers": {
    "picker": { "command": "pick", "args": ["serve"] }
  }
}

Or once for every project this account opens, under mcpServers in ~/.claude.json — the entry is identical. Other clients keep their registrations in their own files; the entry to write into them is the same command and arguments.

No deny list accompanies any of it, because there is nothing to deny. The client has no built-in SQL tool, so wiring pick adds a bounded route without opening any other. The file tools and shells are a different story, and they are fettle's story: on a workstation that runs both programs, fettle's own install is where the built-ins get excluded, and a fettled workstation needs nothing more before it picks.

The MCP front end

pick serve starts the front end on stdio. A client launches it; a person does not — run by hand it waits on stdin, which is correct behaviour that looks like a hang. The tools are named mcp__picker__VERB: mcp__picker__catalogs, mcp__picker__select and so on, and every answer is byte-identical to the CLI's --json mode.

pick VERBpick serve
Started bya person, or a scriptthe client, from the registration above
Boundary fromthe nearest .picker.json upward from the current directory, or --config PATHthe .picker.json where the client launched it — re-read before every call, so an edit binds on the next request
Answers withtext, or JSON under --jsonMCP tool results, byte-identical to --json
Dispatcherthe same one — a verb behaves identically through either

No tool schema carries a connection string, a server name, or a database name. The model cannot point the boundary anywhere; a person edits the two files, and pick refuses to write them.

To check the server is live, ask the assistant for catalogs. It answers with the declared servers and databases without opening a connection. No such tool means no server started — which looks identical to pick not being on PATH, and usually is exactly that.

Updating, and taking it off again

  • Update: replace the file; the next launch is the new build. A running pick serve belongs to the client that launched it and serves the old build until that session restarts — the same rule as every stdio server. Configuration never waits for a restart, only binaries do, because the boundary is re-read on every call.
  • Remove: delete the directory and the PATH entry, and remove the "picker" entry from any .mcp.json that names it. The two .picker files in a project are yours — keep them for the next install or delete them with it. Nothing else was written anywhere.
The machine is ready. Everything from here is per-project and in a fixed order — declare the server and its databases, scope the objects and columns, set up the login, run doctor, then prove a refusal actually refuses: pick in a project.
