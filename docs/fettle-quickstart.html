Shoddy · Fettler

Quick Start

Install it, register it, turn it on in a project, check it. Four steps, one command each. The pages after this one give the detail.

← PreviousThe Fettled WorkstationInstalling ItNext →
You need two things before you start: the archive for your platform from the latest release, and a project folder to turn Fettler on in.

1. Install it

Fettler is one file. It needs no .NET runtime and no installer. In the commands below, X.Y.Z is the version you downloaded.

Windows · PowerShell
$dir = "$env:LOCALAPPDATA\Programs\fettle"
New-Item -ItemType Directory -Force $dir | Out-Null
Expand-Archive fettle-X.Y.Z-win-x64.zip -DestinationPath $dir -Force
Get-ChildItem $dir -Recurse | Unblock-File
$user = [Environment]::GetEnvironmentVariable('Path', 'User')
if ($user -notlike "*$dir*") {
    [Environment]::SetEnvironmentVariable('Path', "$user;$dir", 'User')
}
macOS and Linux
mkdir -p ~/.local/bin
tar -xzf fettle-X.Y.Z-osx-arm64.tar.gz -C ~/.local/bin
xattr -d com.apple.quarantine ~/.local/bin/fettle   # macOS only

Those commands also put the folder on PATH. PATH is the list of folders your terminal searches when you type a command. Now open a new terminal, because the one you used still has the old PATH. Then check it:

fettle --version
fettle 1.0.0
If that says not recognised or command not found, the usual cause is the terminal. Open a new one. The second cause is a typo in the directory. Nothing later on this page works until this line does. The long version is putting it on PATH.

2. Register it once for this machine

Registering tells your assistant that Fettler exists, so the assistant can launch it. Do this once per account, not once per project. --all means every assistant client installed on this machine; clients that are not installed are skipped. --dry-run prints what the real run would do and writes nothing. Run it first, every time.

fettle setup --all --global --dry-run
fettle setup --all --global
changed:
  C:\Users\you\.claude.json  register fettler under mcpServers
note: fettle is on PATH at C:\Users\you\AppData\Local\Programs\fettle\fettle.exe; the
      registration uses the name 'fettle'
note: the machine level declares no tree. In each project, run: fettle setup claude-code
      --local. That creates a .fettler.json declaring the project folder as 'work'
note: not written: Read, Write, Edit, NotebookEdit, Grep, Glob, Bash, PowerShell, Monitor,
      BashOutput, TaskOutput would be denied in C:\Users\you\.claude\settings.json. Pass
      --deny to write the deny list at the global level
A global run registers Fettler and stops there. It declares no tree, so it writes no .fettler.json. It only offers the deny list. The deny list is the settings entry that blocks the assistant's built-in file tools, so that Fettler becomes the only route to files. Adding --deny writes it for every project this account opens. Leave it off for now. Step 3 writes it in one project, where you can see it.

3. Turn it on in a project

Change to your project folder and run this. Use the same --dry-run habit:

fettle setup claude-code --local --dry-run
fettle setup claude-code --local

It writes four files:

changed:
  C:\work\myproject\.fettler.json  created, declaring this folder as 'work'
  C:\work\myproject\.mcp.json  register fettler under mcpServers
  C:\work\myproject\.claude\settings.json  deny the built-in Read, Write, Edit, NotebookEdit, Grep, Glob, Bash, PowerShell, Monitor, BashOutput, TaskOutput
  C:\work\myproject\CLAUDE.md  add a Fettler instruction block
note: the shell is denied too, so build and git commands through it now stop. Allow back
      only the commands this project needs, for example "allow": ["Bash(git status:*)"], or
      declare them as tasks in .fettler.json. Never allow a command that writes files
FileWhat it does
.fettler.jsonThe boundary. Declares this folder as a tree called work. Fettler touches nothing outside it.
.mcp.jsonTells the assistant to launch Fettler.
.claude/settings.jsonDenies the built-in file tools and the shell, so Fettler is the only route rather than one option.
CLAUDE.mdTells the assistant, in words, to use Fettler.
setup and doctor are the only two verbs that run before .fettler.json exists. That is why this step is one command: --local writes the file every other verb needs. Every other verb refuses in a folder with no .fettler.json, and says so.
Your build and test commands stop working at this point. That is the deny doing its job. A shell is a complete way round the boundary, so it is closed by default, and you open only what you need. Either put the command in .fettler.json as a task, or name it in allow, for example "allow": ["Bash(git status:*)"]. Never allow a command that writes files. The shell section explains why.

To use another client instead of claude-code, name it: claude-desktop, vscode-copilot or github-copilot. --all covers every client this machine has.

4. Check it

fettle doctor
fettle 1.0.0  C:\Users\you\AppData\Local\Programs\fettle\fettle.exe
on PATH: C:\Users\you\AppData\Local\Programs\fettle\fettle.exe
tool inventory dated 2026-08-20. Check 2.8 does not know tools added to the client since then

claude-code     global  healthy   registered; runs ...fettle.exe
                        C:\Users\you\.claude.json
claude-code     repo    healthy   registered; runs ...fettle.exe
                        C:\work\myproject\.mcp.json
claude-desktop  repo    n/a       this client has no project level

ways past Fettler on this machine:
  - 2.8  deny does not list the built-in Read, Write, Edit, NotebookEdit, Grep, Glob, Bash,
         PowerShell, Monitor, BashOutput, TaskOutput. Run: fettle setup claude-code --local
      C:\Users\you\.claude\settings.json

The block after the rows is the second half of the report, and the half worth reading. The finding shown here is expected. Step 2 registered the machine and did not touch its deny list, so the global settings file still has nothing in it. Your project is covered. Every other project on this account is not.

WordMeaningExit
healthyregistered, and the command it names starts0
n/anothing to configure at that level for that client. Not a fault.0
absentthe client is installed, and Fettler is not registered with it1
brokenregistered and wrong. Usually the command does not resolve.2

Then restart your assistant. A client reads its server list when it starts. A session that is already running does not have Fettler and will not notice it appear.

If doctor does not come back clean

The report has two halves, and each is fixed in a different place. The wiring is one row per client per level, ending in a verdict. The findings come after it, under ways past Fettler on this machine. Each finding is numbered, and each is a route past Fettler rather than a broken registration.

What you seeWhat to do
on PATH: noStep 1 did not take. Put it on PATH and open a new terminal. Nothing else works until this does.
absentRun step 2 or step 3 for that client and level. The wiring table gives the command per row.
brokenThe registration is there, and its command does not resolve. Run setup again with --command naming the binary, and --force to overwrite an entry that says something else. Details.
A numbered finding: 2.6, 2.8, B.17…Everything doctor can report, and how to clear it has a row per check: what it found, and the edit that clears it.
Exit 1 with no finding you recogniseWarnings only, nothing broken. The four verdicts says which rows count as what.
The three commonest findings on a first run. 2.15: your assistant's scratch directory (the staging folder it writes drafts into) is outside every tree. That matters now that Write is denied. Declare it, as step 2 of setting up a project shows. 2.8 at the global level: expected, since step 2 left the machine-wide deny list alone. 2.17: you run another MCP server, which most people do. It is reported as a fact, not a fault, because the deny list closes names and another server's tools are not called Read.

Prove it, in three commands

Do this once, because the guardrail is the reason to install Fettler. Run these in the project you just set up.

fettle roots
work        C:\work\myproject  (default)
            can: list read create update rename delete

declared by C:\work\myproject\.fettler.json

That is the whole boundary. Now step outside it:

fettle read C:\Windows\win.ini
refused: the path is outside every declared tree. Run roots to see the trees

Exit 4. And the file that grants the permissions cannot be edited by the thing they are granted to:

fettle write .fettler.json --text "x"
refused: .fettler.json is a file that says what this tool and the assistant may do.
Fettler does not write those files. Change it with an editor. The files are:
.fettler.json, .fettler.local.json, .mcp.json, .picker.json, .picker.local.json,
.claude/settings.json, .claude/settings.local.json, .vscode/mcp.json

Exit 11. Both refusals are the same whether a person or an assistant asks. The boundary is read at launch, from a file neither of them can write.
