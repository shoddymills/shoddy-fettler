Shoddy · Picker

Screening

Stop regulated rows leaving a database by accident. The first tier needs nothing installed and one line of configuration.

← PreviousIn a ProjectThe ModelsNext →

This page assumes pick is installed and a boundary is declared. That is installing it and in a project, in that order. The screen is the last thing you switch on, and many boundaries never switch it on. The column scopes and the login already decide what can be asked for.

Read step 1 before anything else. The screen refuses whole result sets. On a database it does not belong on, it will refuse a great deal of ordinary work, starting with every customer table that has an email column. People get out of that by turning it off, which leaves you worse off than never having switched it on. Put it on the databases that hold records about people, and on nothing else.
# 1. decide whether this database needs it     <- many do not
# 2. add "screen" to the database in .picker.json   <- binds on the next call
pick catalogs                                  # confirm what is screened
pick select "SELECT TOP 5 * FROM Customers"    # confirm it refuses

That is the whole feature for most people who want it. Names, addresses, conditions and free text need a model. A model is a second program and a download you fetch yourself. The models is that half, and nothing on this page depends on it.

Do you need this?

Switch it on when a database holds records about people, and a person outside your team could read the transcript. What a select returns goes into an assistant's context, then into a transcript, a log, and whatever ships those onward. The screen sits between the result set and that chain.

The database holdsSwitch it on?
Patient records, encounter notes, lab resultsYes. This is the case the screen was built for.
Customer records with names, addresses, card or account numbersYes, with identifiers at least, which catches the card and account numbers. The names and addresses need a model. See the categories.
Free-text columns nobody audits: notes, comments, support ticketsYes. A free-text column is exactly where an identifier turns up that no scope predicted.
Reference data, lookups, catalogues, order lines with no personal columnsNo. If such objects sit inside a screened database, give them a scope that turns the screen off. Carving out a scope shows how.
Anonymised or synthetic dataNo. A screen here refuses invented identifiers all day and protects nobody.

Note Do not put "screen": true on a working database to see what happens. One of the patterns matches any email address, and customer tables are full of them. Every select that returns one will refuse. That is the detector working correctly, on a database nobody meant to screen. The fix is the scope, or not screening it at all.

What gets screened

The three verbs that disclose what a database holds: select results, describe answers and objects listings. Each hands its payload to the screen before it is serialized, through one seam, so a verb added later that discloses anything has to come through the same door. catalogs and doctor report your own configuration and are not screened.

It judges the payload leaving, never the table. A table may hold clinical notes in row 40,000. A SELECT that discloses none of them is served. Judging the whole table would lock the databases people most need help in, and the way out of that is to turn the screen off.

A query is judged under the union of the scopes it read. Join a screened table to an unscreened one and the response is screened. Any scope the query read from that declares a screen covers the whole result set.

Switch on the first tier

This needs nothing installed. Add "screen" to the database that holds the records, in .picker.json:

"Sales": {
  "can": ["list", "select", "describe"],
  "screen": ["identifiers"],
  "scopes": [
    { "object": "ref.*", "can": ["list", "select"], "screen": false }
  ]
}

Note No restart. pick re-reads the boundary before every call, so an edit to .picker.json binds on the next request. fettle reads its configuration at launch and needs the assistant restarted. This is the one place the two programs' behaviour differs on purpose, because a database boundary is edited far more often than a tree's.

There are three ways to write it, and one that is refused:

You writeIt screens
"screen": trueAll four categories. Forgetting to name one cannot go wrong this way.
"screen": ["identifiers", "clinical"]Only those two. A bare list includes.
"screen": ["-scientific"]Everything except scientific. A list of - words excludes.
"screen": falseNothing. This is also what a database that says nothing gets.
"screen": ["identifiers", "-scientific"]Refused when the file is read. It reads either as "identifiers only" or as "everything but scientific", and those differ by two whole categories. Nothing here guesses which you meant.

A misspelt category is refused too. "lgal" would quietly subtract a screen, and you would not find out until data left a database you believed was covered.

Note Three regulation-shaped words are refused outright, and the refusal says what to write instead. phi, pii and sci name a regulation rather than what runs. Each promises coverage that only arrives once a model is installed, while reading as though it were there from the start.

The four categories

WordConcernWhat carries itWhich model
identifiersStructured identifiers, whoever they belong toSix patterns, running inside pick. The only category that works with nothing installed.None, ever. It never crosses the sidecar's pipe and never asks for a model.
clinicalClinical text, the HIPAA concernA model you install, and nothing until you do.A de-identification fine-tune from the BioBERT or ClinicalBERT family. The models page is the walk-through.

clinical, legal and scientific screen nothing until you install a model. None of the three has a pattern behind it. A database that names one of them and has no models directory declared is screened in name only. Tier one is the whole screen, and a clean result means the patterns found nothing, not that a model looked. Naming the directory is the act that changes it.
The other side of that, and the more important half: out of the box the screen catches structured identifiers. A social security number, a valid card number, a formatted phone number, an email address, a labelled record number and a labelled date of birth. Names, addresses, conditions and free text are caught only by a model you install. A database screening identifiers alone is protected against the first list and nothing beyond it.

What the patterns catch

These run inside pick itself. There is no model, no second program and no new download. They are the same six detectors fettle runs, byte for byte, and a verifier in this repository holds the two programs' pattern sets equal.

DetectorMatchesDeliberately not matched
ssnthe hyphenated form, excluding every range the Social Security Administration does not issuenine bare digits, which are an order number far more often than a person
credit-card13 to 19 digits in the groupings cards are written in, passing the Luhn check digitthe same shape failing Luhn, and bare digit runs. A column of reference numbers must not deny every page of the table
phonea leading +, or a separated groupingten bare digits
emailthe ordinary address shapenothing
medical-record-numberan identifier under its own label: MRN:, patient idbare identifier-shaped strings, which would refuse every part number in every table
date-of-birtha date under its own label: DOB:, date of birthbare dates, which a database is full of

All six are one category, and that is the point of the name. They are all identifiers with a shape somebody fixed or a label announcing them. None of them reads clinical language, and a refusal from any of them reports as identifiers, never as a judgement about what kind of table it came from.

The patterns run over the serialized rows, the payload exactly as it would leave. So a labelled MRN: line inside one notes cell is found the same way it would be in a document.

Carving out the objects that do not need it

A scope's screen replaces the database's, exactly as its can does. That is what lets a scope take screening away from reference data inside a screened database:

"Sales": {
  "can": ["list", "select", "describe"],
  "screen": true,
  "scopes": [
    { "object": "ref.*",     "can": ["list", "select"], "screen": false },
    { "object": "dbo.Notes", "can": ["list", "select"], "screen": ["identifiers", "clinical"] }
  ]
}
  • A scope that says nothing about screen inherits. Reading silence as "screen nothing here" would punch a hole in the first database anyone switched it on for.
  • screen is not a verb. The grants are named after what may be asked of an object. A screen is a property of content leaving the boundary, and it sits beside can, not inside it.
  • The screen is a net under the scopes, not a substitute for them. A column somebody can name as sensitive belongs in a column exclusion, where the boundary removes it every time, before the screen ever sees it. The screen exists for what nobody predicted: an SSN pasted into a notes column, an email in a free-text field.

Check it, then prove it

Ask for the catalogs. The edit already binds, with no restart needed:

$ pick catalogs
warehouse  (connect: Server=db.internal;Database=Sales;...)
  Sales: list select describe  [screen: identifiers]
    ref.*: list select  [screen: nothing]
source: /work/shoddy/.picker.json

The [screen: …] marker appears only where a screen is on, and a scope shows one only where the scope itself states one. A scope with no marker is inheriting. A models: line appears once a models directory is declared. No line means no second tier, and the model-backed categories are screened in name only.

Prove it refuses

The configuration being right and the screen holding are two different claims, and only the second matters. With synthetic rows (invented SSNs, fabricated customers, never real ones), select something you know carries an identifier:

$ pick select "SELECT name, notes FROM dbo.Intake"
refused: this response would disclose regulated data: 1 in identifiers. The matches are
not quoted, because the refusal would then disclose them. Select fewer columns or
rows, or take the screen off this scope if the content is not regulated.
$ echo $LASTEXITCODE
13

A category and a count, and never the value itself. A refusal that named what it found would write it into the log and the transcript, which is the harm the screen exists to prevent. Every screening refusal answers 13, and no rows are trimmed. A result set with the offending rows quietly removed would be a fabricated answer with a clean verdict.

When it refuses and you did not expect it

Every refusal names its own cause. Read the first few words. They say whether something was found, or whether the screen could not run. Those are different problems.

It saysDo this
this response would disclose regulated data: Working as intended. Select fewer columns or rows, or take the screen off that scope if the content is not regulated. The count tells you how many entities, and the category tells you which kind.
this response could not be screened, so it is not served: The second tier broke, and what follows names the piece: the burler sidecar missing from beside pick, a model absent from the directory, a child that died or ran out of time. Nothing was checked, so nothing is served. pick doctor reports the two facts these depend on, whether the models directory exists and whether burler sits beside the program. Driving burler by hand shows the sidecar's own answer in full.

Why every one of these refuses

Serving content because the check broke is the one outcome this must never produce. A sidecar that will not start, a model that will not load, an answer nobody can parse, and an inference that ran out of time all refuse with exit 13 and say which. So does a tier-one pattern that ran out of time on a huge payload. The one thing a served result can never mean is that nothing was checked.

It reads as an outage, and that is the intended trade. A screen that quietly stopped screening would be worse in the way that matters.

What it costs

WhenWhat happens
Every screened response, alwaysThe patterns run in pick itself. Each has a one-second ceiling, and in practice they are not measurable against a network round trip.
The first model-screened response after a quiet spellburler starts and loads a model. Seconds. The wait is allowed up to 90 of them, because a timeout here would deny a disclosure that was going to be served.
Every response after thatTens of milliseconds. The child is kept warm. Thirty seconds is the point at which something is wrong rather than slow.
Five minutes with nothing to screenThe child is killed and its memory released.
A database screening identifiers aloneNever starts burler at all. Tier one was the whole judgement, and it ran in process.

What it does not do

This is a safety net, not a boundary, and the difference matters. Named-entity models miss entities. Patterns miss anything written a way they do not expect. An identifier split across two concatenated cells defeats every one of them. A clean verdict is evidence of absence and never proof of it. The boundary is the column scope, the grant and the least-privilege login. The screen is the net under them.
It does notBecause
Offer a confidence settingAny detection refuses. A setting gets turned until the check is off.
Trim, redact or mask rowsIt refuses the whole response. A result set with holes in it would look like a safe copy of the answer, and would not be one.
Judge what stays in the databaseIt reads the payload leaving, never the tables. A screened database is not a scanned database.
Stop anything outside pickSSMS, sqlcmd, a BI tool or a person with the connection string reads the same rows unscreened. The screen sits on pick's answers, and only there. The least-privilege login is the wall that holds for every client.
Certify a regulationThe categories name what runs, patterns and models, never a statute. Nothing here is "HIPAA compliance", and reading it that way is the misunderstanding this row exists to prevent.
