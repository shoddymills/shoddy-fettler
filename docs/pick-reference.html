How a name resolves

  • A three-part name — Sales.dbo.Customers — resolves against the declared databases and nothing else. A database the file does not declare answers exactly as a table that does not exist.
  • A two-part or bare name — dbo.Customers, Customers — is searched for across the declared databases; the connection's own default database is never consulted. If two declared databases both hold a match, the query is refused as ambiguous, naming both, and the fix is to qualify.
  • A name defined by a CTE in the same query wins over a declared object of the same bare name — the standard T-SQL precedence, kept.
  • A four-part name is refused outright — a linked server is a second server wearing a prefix.
  • Hidden is absent, everywhere. An object with no list grant is missing from objects, excluded from bare-name search and its ambiguity, and refused as nonexistent when named directly — one wording, one factory in the code, so the refusals cannot drift apart and be told apart.
  • Listed but not granted is refused honestly instead, naming what the scope does grant — because the listing already disclosed that the object exists.
  • One server per statement. A query may join across declared databases on the same server; it may not span servers.

The verbs, in detail

Five verbs, identical through the CLI and the MCP server — the MCP answer is byte-for-byte the CLI's --json output. --config PATH names a configuration explicitly; otherwise the nearest .picker.json upward from the current directory governs.

The query gate

Every statement is parsed to a syntax tree before anything touches a connection, and the tree is walked against an allowlist of constructs the gate understands. Anything the walk does not recognise refuses the whole statement — fail closed, so a T-SQL feature added next year arrives refused rather than unexamined.

RefusedWhy
anything but one SELECTINSERT, UPDATE, DELETE, MERGE, EXEC, DECLARE, USE, transactions, and a second statement in the batch are each refused with their own stated reason
SELECT … INTOa write wearing a SELECT's clothes
OPENROWSET, OPENQUERY, OPENDATASOURCEeach is a connection string in a query — a whole second boundary smuggled into one function call
user-defined functionsa function body is code the gate cannot see through
variables and table hintsoutside the closed surface; refused by name rather than by the generic arm
four-part namesa linked server is a second server wearing a prefix
sys.*, INFORMATION_SCHEMA, OBJECT_DEFINITION and relativesthe catalog answers questions the scopes exist to govern; describe answers them governed

What passes is rewritten before it runs. Every table and view reference is rewritten to its full bracket-quoted three-part name, so the statement that reaches the server can only mean what the gate approved. SELECT * is expanded to the columns this caller is actually permitted — the star never reaches the server — and the answer states the column list it chose. CTEs, subqueries, derived tables, APPLY and set operations are walked the same way; a query is approved whole or refused whole.

Column scoping, everywhere a column can appear

A scope may grant every column, name the columns it includes, or name the ones it excludes — the grammar lives with the configuration. Enforcement is the reference's half:

  • A hidden column is checked everywhere: the select list, WHERE, ON, GROUP BY, ORDER BY, inside expressions, inside subqueries. WHERE ssn = … would let a caller reconstruct a column it cannot read, one predicate at a time, so it is refused.
  • Refused in the same words as a column that does not exist, naming no table — so the refusal cannot be used to learn that the column is there. Hidden and absent are one answer, deliberately.
  • SELECT * is never an escape. The star expands to the permitted columns before the server sees it, and the answer states the list, so what was left out is a fact about the grant rather than a surprise in the rows.

DESCRIBE, and what a view will not say

describe answers from the catalog: columns with their types and nullability, indexes, and foreign keys — never by running the object. Hidden columns are absent from all of it, and an index or key that involves a hidden column is left out whole, because a summary that says "one column not shown" says a hidden column exists. Every answer carries a shape hash, so a caller can tell when an object changed underneath it.

A view answers its columns and never its definition. View text embeds the tables underneath, their join logic and their filters — exactly the structure the scopes may be hiding — so the stored CREATE VIEW text is denied in full rather than summarised. No opportunities to leak.

Caps, stated in the answer

  • 100 rows by default (--limit N raises or lowers it); a capped result states how many rows were withheld.
  • 2,000 characters per cell, 40,000 per answer — truncation is announced, never silent.
  • 30 seconds per query; a query that outruns it is timed-out, its own outcome, never dressed as anything else.

Exit codes

Each distinct failure class gets its own code, so a script can branch on $LASTEXITCODE without parsing text. The numbers are fettle's numbers where the words match, so a script driving both tools branches one way; the gaps in the sequence are fettle's outcomes this tool cannot produce (a stale hash, a governed file), and they stay gaps rather than being reused for different words. A verifier in this repository holds the table below to the source, row by row, and holds the alignment itself.

CodeOutcomeMeaning
0okit worked
1—an unexpected internal fault
2invalidthe request did not make sense — an unknown flag, a missing value, a malformed configuration
3not-foundnot there, or not there as far as anyone can learn — an object outside the grant answers exactly as one that does not exist
8refusedpick declined, for a stated reason — a verb the grant withholds, a query the gate will not pass
9deniedthe server, the network or the OS declined, which is not pick declining — a login without rights, a connection that will not open
10timed-outthe query outran its 30 seconds and was cancelled
13screenedthe response would have disclosed regulated data out of a screened scope — or the screen that would have judged it could not run. See screening

denied and refused are kept apart on purpose: a login failure reported as a gate refusal sends the caller to debug a boundary that is working.

What this defends against, and what it does not

  • The threat is inadvertent assistant action, not a determined person. Whoever owns the machine edits .picker.json in an ordinary editor and holds the real credentials. That is the design, not a hole — the same bound Fettler draws.
  • The statement that reaches the server is never the caller's string. It is the gate's rewrite of a parsed tree: three-part bracket-quoted names, the star already expanded, every construct one the allowlist recognised. What the parser cannot parse never leaves the process, and what it parses to something outside the allowlist is refused whole.
  • The login is the second wall, and it is the server's. pick enforces its boundary in pick; a login granted only SELECT and VIEW DEFINITION means even a fault in pick has nothing wider to spend. Declaring a database grants the login nothing — doctor reports a refused knock rather than letting the declaration imply access.
  • What it does not defend against: a hostile server administrator, a poisoned catalog answering false metadata, or data a permitted column legitimately holds — that last is the screen's territory, and the screen is a safety net rather than a boundary. A clean verdict is evidence, never a certificate.
