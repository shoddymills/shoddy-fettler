In a Project

Declaring servers, databases, scopes and columns; the two files they live in; the login to connect as; and proving the wiring with doctor.

Two files, dividing by what belongs in source control

.picker.json is checked in and declares the surface — servers, databases, verbs, scopes, columns, screens — and is reviewed like the boundary it is. Pick finds it by walking upward from the current directory, the way Fettler finds the tree file; --config PATH names one directly.

{
  "servers": {
    "warehouse": {
      // the connection is in .picker.local.json, below
      "databases": {
        "Sales": {
          "can": ["list", "select", "describe"],
          "screen": ["identifiers"],
          "scopes": [
            { "object": "dbo.Customers", "can": ["list", "select"],
              "columns": ["-ssn", "-dob"] },
            { "object": "audit.*", "can": [] }
          ]
        }
      }
    }
  }
}

.picker.local.json sits beside it, kept out of source control, and holds what never belongs in source control: the connection strings, and the per-machine models directory for the screen's second tier.

{
  "models": "C:/screening-models",
  "servers": {
    "warehouse": {
      "connect": "Server=warehouse.internal;Database=Sales;Integrated Security=true;TrustServerCertificate=true"
    }
  }
}
  • The local file cannot widen the surface. It supplies connect and models for what the checked-in file declares — and nothing else. A database declared only locally refuses the load, because it would be a boundary nobody reviewed.
  • Two ways to say the connection, and the overlay wins. Either the local file carries the string, as above — or the checked-in file names an environment variable, "connect": "env:WAREHOUSE_SQL", and nothing secret sits in either file. Naming both is legal, and the overlay's wins; an example should pick one, so this page's picks the local file.
  • A password literal in the checked-in file refuses the whole load, with directions to the local file or an env:NAME variable. The reviewed file is the one that ends up in source control and in every copy of the project.
  • An unknown word anywhere refuses the load, naming the valid set. A misspelt verb or category would otherwise silently withhold a grant or a screen, and the failure would arrive much later as a refusal nobody can explain.
  • Neither file is ever written by pick. A person edits them, and serve re-reads both before every call — an edit binds on the next request.

Who can write these two files is the whole game

The pair is pick's trust root: rewrite them and the very next call obeys the edit, because the boundary is re-read every time. pick itself cannot touch them — it has no write path at all — but some other tool the assistant holds probably can, and that is the door to close.

  • On a workstation that also runs fettle, the door is already closed. Both names are on fettle's governed list, refused by every fettle write path at every permission level — on exactly the terms fettle refuses its own .fettler.json.
  • Running pick without fettle? At a minimum, set both files read-only so an assistant's file tools cannot casually rewrite them:
Windows · PowerShell
Set-ItemProperty .picker.json, .picker.local.json -Name IsReadOnly -Value $true
macOS and Linux
chmod a-w .picker.json .picker.local.json

Note The attribute is a speed bump, not a wall. A tool that can run a shell can clear it in one command — which is the argument for the fettled workstation, where the shells and built-in file tools are denied and the governed list holds instead.

Scopes replace; the most specific wins

A scope names an object pattern — schema.object, with * standing for a whole segment — and what it grants replaces the database's grant outright for the objects it matches. An exact object beats an exact schema; an object matching no scope gets the database's own can and screen. What a table gets is read from one line, never assembled from several.

  • A scope states its verbs: "can": [] is how audit.* above hides a whole schema — absent from listings, and refused as nonexistent everywhere else.
  • columns is true (everything), a bare list (only these), or a - list (everything but these); mixing the two forms is refused rather than resolved.
  • screen on a scope replaces the database's; silence inherits it — the same rule Fettler's scopes follow, for the same reason.

More than one database, more than one server

servers and databases are both plural on purpose. The ETL shape — a staging database beside the warehouse, an operational server beside the reporting one — is one configuration:

{
  "servers": {
    "warehouse": {
      "connect": "env:WAREHOUSE_SQL",
      "databases": {
        "Staging": { "can": ["list", "select", "describe"] },
        "Sales":   { "can": ["list", "select", "describe"],
                     "screen": ["identifiers"] }
      }
    },
    "ops": {
      "connect": "env:OPS_SQL",
      "databases": {
        "Orders": { "can": ["list", "describe"] }
      }
    }
  }
}
  • A query may join across databases on the same server. SELECT … FROM Staging.load.Batch b JOIN Sales.dbo.Orders o ON … is one statement down one connection, each reference rewritten to its three-part name, each object's own scope, columns and screen applied — a response is screened under the union of the scopes it read.
  • One server per statement. A query reaching objects on two servers is refused naming both, because a connection speaks to one of them. Compare across servers as two selects — which is also the honest shape: pick discloses result sets, it does not fabricate a joined one no server produced.
  • An unqualified name is proven unique across every declared database before it resolves — the connection's default database is never consulted. A bare name matching in two databases is refused naming both places; qualify it. Every database declared is therefore part of every name's proof, so declare what you use.
  • The same database name on two servers cannot be told apart by a name, so naming it is refused. The declared name is the name the rewrite sends to the server — renaming a declaration is not a remedy — so declare it on one server per configuration and reach the other through its own .picker.json (--config names one directly).
  • Each server carries its own connect — and its own least-privilege principal, which is the next section: least privilege is per server, per database.

Connect as a login that could not do more anyway

Pick's boundary is enforced in pick. The server has its own, and the two should agree: connect as a login granted only SELECT and VIEW DEFINITION on the declared databases, so that even a fault in pick has nothing wider to spend. The honesty clause runs the other way too — declaring a database in .picker.json does not grant the login anything, and doctor reports a server that refuses the knock rather than letting the declaration imply access. A login failure is reported as the server declining (denied), never as the gate refusing (refused), so nobody debugs a boundary that is working.

Creating a SQL login is optional — one way to hold the principle, not a requirement. Most shops connect with integrated security — Integrated Security=true, the connection arriving as a Windows or Entra account, no password anywhere — and least privilege carries over unchanged: the grants attach to whatever principal connects. Grant the same two permissions to that account, to a group, or to a database role the account is a member of; only the name in the T-SQL changes.

The grant, in full — run once by an administrator, and the whole of what pick's principal can ever do. With a dedicated SQL login:

CREATE LOGIN pick_reader WITH PASSWORD = 'a-strong-generated-password';
USE Sales;
CREATE USER pick_reader FOR LOGIN pick_reader;
GRANT SELECT          TO pick_reader;   -- the rows
GRANT VIEW DEFINITION TO pick_reader;   -- the metadata describe reads

With integrated security, the same two grants land on the account or its group — or sit in a role, so that membership is the only thing that ever changes:

CREATE LOGIN [DOMAIN\report-readers] FROM WINDOWS;  -- a group: membership stays AD's job
USE Sales;
CREATE USER [DOMAIN\report-readers] FOR LOGIN [DOMAIN\report-readers];
CREATE ROLE pick_reading;
GRANT SELECT, VIEW DEFINITION TO pick_reading;
ALTER ROLE pick_reading ADD MEMBER [DOMAIN\report-readers];

On a development machine with LocalDB, integrated security stands in for all of this — the instance is yours alone. On anything shared, the GRANT lines are the whole ceremony. With a SQL login the password goes in .picker.local.json or an environment variable, never in the checked-in file — and with integrated security there is no password to put anywhere.

Prove the wiring

pick doctor     # the configuration, a bounded knock on each server,
                # the models directory, burler beside the program
pick catalogs   # the declared boundary - no connection opened
pick objects    # what this caller may actually see

doctor never prints a connection string or a credential — it says whether the knock was answered, not what knocked.

Verifying the boundary

Prove it, don’t trust it. The wiring being declared correctly and the boundary holding are two different claims, and only the second one matters. Run each of these — or ask the assistant to — and watch what comes back:

Try to…A correct setup…
select from a database the file does not declarerefuses, exit 3 — in the same words as a table that never existed, whether or not the database is real
select from an object whose scope is "can": []refuses, exit 3 — and objects never listed it
select a column the scope excludes — then filter on it with WHERErefuses both, exit 3, in the words of a column that does not exist
SELECT * from that same tableserves — every column except the excluded ones, and the answer states the column list it chose
run DELETE, EXEC, or a second statementrefuses, exit 8, each with its own stated reason
read sys.tablesrefuses, exit 8 — the catalog answers through describe, governed
connect with the login and a plain SQL client, and try an INSERTthe server refuses — the login's grant stops at SELECT, so even around pick there is nothing wider to spend
edit .picker.json, then call again without restartingthe change binds — the boundary is re-read before every call

With a screen declared, add the screening rows — proving it refuses has that half.

Wiring the MCP server into a client

The server is pick serve on stdio. Register it in the project that should see it — for Claude Code, .mcp.json in the project directory:

{
  "mcpServers": {
    "picker": {
      "command": "pick",
      "args": ["serve"]
    }
  }
}

The five tools it offers are the five verbs, and every answer is byte-identical to pick VERB --json. A changed .picker.json binds on the next call; a changed binary needs the session restarted.
