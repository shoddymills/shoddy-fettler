Shoddy · Fettler

In a Project

Six steps, in the order they depend on each other. Declare the boundary, wire the client, prove the refusals.

← PreviousInstalling ItScreeningNext →

This page assumes fettle is already on the machine and registered. That is installing it, done once. What follows is per project. Each step needs the one before it.

Write .fettler.json first, before you run anything. It declares your trees, and until it exists this project has no boundary. The server learns its trees at launch, from the .fettler.json in the folder it starts in. Declaring nothing is a refusal, not a fallback to the current directory. setup --local creates the file if none is there, and it is the only thing that does. But what it writes is the bare minimum, {"trees":{"work":{"path":"."}}}, and it never revises one afterwards. A generated file nobody read is still the boundary you are running under. Write it yourself, and you know what it says. setup and doctor are the two verbs that run without one. Everything else refuses until it exists.
# 1. write .fettler.json in an editor          <- your boundary; nothing below writes it
# 2. add .fettler.local.json for the scratch   <- not checked in; this machine's own
# 3. add "tasks" if anything needs running
fettle doctor                                  # what is wired, and what goes round it
fettle setup claude-code --local --dry-run     # what would change
fettle setup claude-code --local --hooks       # change it
fettle doctor                                  # confirm, and see what is left by hand

The last step matters. setup clears the findings whose fix is an addition. Every finding whose fix is a removal (2.6, 2.7, 2.11, 2.14 and B.17) is still there afterwards, and still yours to do.

1. Declare your trees

A tree is a path and a set of permissions. You may declare more than one. A folder of code, a sibling folder and a scratch directory is the ordinary case. A file at the top of the project says it once, so nobody types a boundary onto every command.

Put it at the top of the project, named .fettler.json, and check it in. The smallest useful one is a single tree:

{
  "trees": {
    "work": {
      "path": ".",
      "can": ["list", "read", "create", "update", "rename", "delete"]
    }
  }
}

A fuller one, with a second tree kept read-only and a folder inside it hidden:

{
  "trees": {
    "work": {
      "path": ".",
      "can": ["list", "read", "create", "update", "rename", "delete"]
    },
    "requirements": {
      "path": "../shoddy-requirements",
      "can": ["list", "read"],
      "scopes": {
        "backlog":           { "can": ["list", "read", "create", "update", "rename"] },
        "backlog/cancelled": { "can": [] }
      }
    }
  }
}
  • The tree the file sits in already grants everything but execute, so "can" may be left off it. Every other tree defaults to list read, and only a configuration file can widen that.
  • A scope replaces what its tree grants. It does not add to it. A scope naming create and nothing else grants create and nothing else, not even read. The rules are on the reference page.
  • Paths are relative, forward-slashed, with no drive letter. They resolve against the file, not against whoever is calling. That is what lets the file be checked in. The spelling table has the cases.
  • A tree that does not exist is a startup failure. So the checked-in file can only name trees that travel with the project. Anything else belongs in the overlay below.
  • A malformed file is refused, never fallen back from, because a silent fallback usually widens the boundary.

Check what you wrote by asking for it back:

$ fettle roots
work          /work/shoddy  (default)
              can: list read create update rename delete
requirements  /work/shoddy-requirements
              can: list read
              backlog  can: list read create update rename
              backlog/cancelled  can: nothing

declared by /work/shoddy/.fettler.json

The personal overlay

An uncommitted .fettler.local.json beside the checked-in file is merged over it. Your machine's own trees need not be typed on every command, and need not appear in everybody else's checkout.

A name in both files means the overlay's version wins entirely, not field by field. Nobody reading two files side by side could say what a field-level merge produced without running it.

2. Declare the scratch tree

Do this before the deny list lands, not after. An assistant stages work (a long replacement, a generated file, a patch it is about to apply) in a scratch directory the harness gives it, outside your source tree. Deny the built-in Write and that route shuts. The scratch is outside every declared tree, so Fettler will not write there either. Both routes are closed, and you find out at the first staging write, not while running setup.

It goes in the uncommitted overlay, because the path is this machine's and nobody else's:

// .fettler.local.json  - beside .fettler.json, kept out of source control
{
  "trees": {
    "scratch": {
      "path": "C:/Users/you/AppData/Local/Temp/claude/<project-folder>",
      "can": ["list", "read", "create", "update", "rename", "delete"]
    }
  }
}
  • Declare the project folder, not its parent. The parent holds every project's scratch, and a session working on one tree has no business writing into another's.
  • Not the per-session folder either. It changes every session, and a declaration that has to be rewritten that often stops being written.
  • No execute, which is never a default anyway. A scratch tree is for staging text, not for running what is staged.
  • fettle doctor reports a missing scratch tree as 2.15, and stops once a tree inside it is declared.

Why setup cannot do steps 1 and 2 for you

.fettler.json and .fettler.local.json are the files that say what Fettler may do, and Fettler refuses to write them at every permission level. setup is bound by the same rule. If it could declare a tree, it could grant itself any tree, and the refusal that makes every other rule hold would mean nothing. It may create a starter .fettler.json where none exists. It never changes one. So it names the fix, and a person applies it. Findings 2.6, 2.7, 2.11 and B.17 work the same way: setup reports them and does not clear them.

3. Declare your tasks

Do this only if something in this project needs running. run executes only what the configuration declares, and never composes a shell command. It also needs the tree to grant execute, which is never a default:

{
  "trees": {
    "work": { "path": ".", "can": ["list", "read", "create", "update", "rename", "delete", "execute"] }
  },
  "replacements": {
    "feature-branch": "hebdenbridge"
  },
  "tasks": {
    "build":   { "run": "pwsh -File shoddy-build.ps1" },
    "gate":    { "run": "node scripts/gate/driver.mjs gate --resume", "cwd": "." },
    "sign":    { "run": "signtool sign /f \"C:\\keys\\my cert.pfx\" bin/app.exe" },
    "feature": { "run": "pwsh -File scripts/shoddy-feature.ps1 new {feature-branch}" }
  }
}
  • Name the binary that is installed. A task naming pwsh on a machine that only has Windows PowerShell fails at launch, not at declaration time.
  • A task takes no arguments from its caller. A variant is a second declared task, or a value the file declares. The command grammar is exact about quoting and backslashes.
  • A value that changes every time goes in replacements. The branch to cut, or the note to commit under, cannot be a second task, because it is a fresh string each time. Declare it once, name it in the command line, and keep the value in the personal overlay, so today's branch name never lands in source control. What a replacement means is on the reference page. Only an identifier between braces is a name, so a brace already on a command line keeps its meaning.
  • cwd, the folder the task runs in, is optional. It defaults to the top of the default tree, and is checked for containment like any other path.
  • Prefix scripts and task names with your project's own name. Use shoddy-build.ps1 rather than build.ps1, and a checkin task rather than commit. An assistant's own permission layer reads these names, and a task named with a bare git word can be refused as if it were the raw command it resembles.
That configuration is trusted input. Containment guards paths. It does not and cannot guard a command list, which is read from a file inside the tree Fettler was pointed at. Whoever can write that file chooses what a caller, a model included, can execute.

3a. Screen what leaves a tree, if it holds regulated data

Skip this unless a tree holds health, consumer-report or education records. The screen is off everywhere until a tree asks for it, and asking is one line in the file you have just written:

{
  "trees": {
    "records": {
      "path": "../records",
      "can": ["list", "read"],
      "screen": ["identifiers"]
    }
  }
}

identifiers is the tier that works with nothing installed. It catches identifiers with a fixed shape or an explicit label. The other three categories, clinical, legal and scientific, screen nothing until you install a model, and fettle roots says so in plain words.

The screen is a safety net, not a boundary. A clean verdict is evidence of absence, never proof of it. Screening is the whole procedure: what each category covers, how to prove a refusal refuses, and what the screen does not do. The models is the other half, for the three categories that need one.

4. Run fettle setup

fettle setup <client> | --all [--global | --local] [--dry-run] [--force] [--hooks] [--deny] [--command PATH]

  clients: claude-code · claude-desktop · vscode-copilot · github-copilot

It is a command rather than a .ps1 and a .sh, so there is one implementation instead of two that must be kept in step by hand.

Every flag, and what it decides

FlagWhat it does
<client>One of claude-code, claude-desktop, vscode-copilot, github-copilot.
--allEvery client this machine has. Clients that are not installed are skipped, not created.
--localThe repository level: .mcp.json, .vscode/mcp.json, .claude/settings.json. Reviewable in source control, and affects this tree only. The deny list is written here by default. Asking for setup in a project is asking for Fettler to be the route in it.
--globalThe machine level, covered on installing it. The registration is written. The deny list is only offered, and needs --deny as well.
--denyWrite the deny list at the global level too. It is a separate flag because changing how the assistant may work in every project is not a side effect of configuring one.
--hooksAdd the SessionStart hook that runs doctor. Claude Code only, opt-in, and added once however often you re-run. It does not depend on whether the deny list needed changing, so asking for it on a project that is already denied still installs it. What it writes.
--command PATHRegister a full path instead of a bare fettle. Use this when the binary is deliberately not on PATH.
--dry-runPrint the same report and write nothing. Run this first.
--forceOverwrite an existing fettler entry rather than leaving it alone. Needed when a registration is broken and has to be replaced.

It merges into JSON and never overwrites. These files hold other people's servers, other people's permission grants, and a hook array that is already doing something. Setup reads the file, adds or updates Fettler's own key, and keeps everything else. Before its first write it makes a backup at <file>.fettler-backup and says where that went. --dry-run prints what it would do and touches nothing.

What it will and will not correct

  • It corrects the wiring: a missing or wrong registration, a missing .fettler.json, a missing instruction block, a missing hook.
  • It does not silently correct policy. An existing allow entry is your own configuration, and removing it changes how you work. Setup names the conflicting entries and leaves them.
  • It cannot correct installation. A binary that is not on PATH is not a configuration edit. Setup says so, rather than writing a registration it knows will fail to launch.
  • It creates a .fettler.json at --local, and never changes one. Creating where none exists is scaffolding. Rewriting one is the escape the rule-file refusal closes, and belongs to a person with an editor. --global declares no tree and so writes no such file. What --local creates declares the folder as work and nothing more, which is why step 1 still comes first.

Running it a second time changes nothing, for the JSON and for the instruction block alike. A registration that already says something different needs --force, so setup never quietly reshapes somebody else's choice.

5. Run fettle doctor

Doctor answers two questions: is Fettler wired into each client, and is anything on this machine letting the assistant go round it.

fettle doctor [--json] [--quiet] [--hook] [--client NAME]
  • It checks every client at both levels, every time. --client narrows the report, never the scan. So "it looked fine" can never mean "it only looked at one".
  • It never writes. Diagnosis and repair are separate verbs, so a check run in a session hook can never change a machine. Repair is setup.
  • It never prints a secret. ~/.claude/.credentials.json sits in the same directory as files it reads. It names files and keys, never values.
  • Exit 0 wired, 1 warnings, 2 broken, so a script can gate on it. --hook always exits 0.
$ fettle doctor
fettle 1.0.0  C:\tools\fettle\fettle.exe
on PATH: no. A registration that names a bare 'fettle' cannot start it
tool inventory dated 2026-08-20. Check 2.8 does not know tools added to the client since then

claude-code     global  absent    'fettler' is not registered in this file
                        C:\Users\you\.claude.json
claude-code     repo    broken    the registration runs 'fettle', and nothing on this
                                  machine has that name. fettle is not on PATH
                        C:\work\tree\.mcp.json
claude-desktop  repo    n/a       this client has no project level

ways past Fettler on this machine:
  ! 2.7  allow lists built-in tools that Fettler replaces: Read(//c/work/**). Remove
         those entries
      C:\Users\you\.claude\settings.json
  - 2.8  deny does not list the built-in Read, Write, Edit, NotebookEdit, Grep, Glob,
         Bash, PowerShell, Monitor, BashOutput, TaskOutput. Run: fettle setup
         claude-code --local
      C:\work\tree\.claude\settings.local.json
  - 2.17 1 other MCP server is registered here: sparky. The deny list does not cover
         its tools. Deny mcp__<name>__* for any that should not reach files
      C:\Users\you\.claude.json

The report has two halves. The wiring is one row per client per level, ending in a verdict. The findings are numbered, and each one is a way round the boundary. ! means serious. - means worth knowing. Everything doctor can report, and how to clear it gives a row per check: what it found, and the edit that clears it. Because setup adds and never deletes, any finding whose fix is "remove" is yours to make in an editor.

The four verdicts

VerdictMeansExit
n/aThe client is not installed, or has nothing at this level. Claude Desktop has no project level, so its repo row is always this.never a failure
absentThe client is installed, and Fettler is not registered with it.warning
brokenRegistered and wrong: the command does not resolve, the configuration is not valid JSON, or a tree does not exist.failure
healthyRegistered, and the command it names resolves.none

6. Verify the guardrails

The wiring being right and the boundary holding are two different claims, and only the second one matters. Ask the assistant to do each of these, and watch what comes back.

Ask the assistant to…What a correct setup does
list the tools it hasfettler appears, and doctor is among the verbs
ask for the rootsthe trees come back with what may be done in each, not only where they are. They are the trees you declared in step 1
read a fileit uses the Fettler tool, and the answer carries an encoding, a line ending and a hash
read /etc/passwd or C:\Windows\win.inirefused as outside every declared tree, exit 4, in the same words whether or not the file is there
write .fettler.jsonrefused as governed, exit 11, whatever the tree grants
write .claude/settings.jsonrefused as governed too. A model does not edit the file naming the tools it may call
write a file containing an AWS key or a PEM private-key headerrefused as credential, exit 12, naming the line and the detector but never the secret
run a task in a tree with no executerefused, exit 8, naming the missing grant
edit a file with the built-in editorrefused by the deny list, and it reaches for Fettler instead
stage something in its scratch directoryit writes, because step 2 declared that tree. If this one fails, that is the step that was skipped
A changed .fettler.json needs the server restarted. The MCP server learns its trees at launch and does not re-read them, so a tree you added mid-session is not there yet. This is the same property that stops a model widening its own boundary, met from the other side.
