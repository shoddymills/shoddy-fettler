## Breaking

- **The home folder is never the implicit tree, nor is the root of a disk,
  nor any folder above home.** 2.0.1 made a folder with no configuration
  file work by taking the launch folder as one tree called `work`. That
  stays, for a project folder. But a client with no project, Claude
  Desktop among them, starts the server in the home folder or at the root
  of the disk, and 2.0.1 then handed the assistant the whole home folder,
  or the whole disk, read and write, with no file saying so. fettle now
  refuses, with exit `8` (`refused`), when no configuration declares a
  tree and the launch folder is one of those three. The message says
  which it was and names the way out: start fettle in a project folder,
  pass `--root PATH` for read-only access, or pass `--config PATH` naming
  a file whose `guardrails` section declares the trees. A declared tree is
  never checked this way, because a person wrote it down. `setup` and
  `doctor` still run from anywhere, since neither resolves a path through
  a tree.

## Fixed

- **`setup tools` writes the deny list and the instruction block.** It
  registered the server and nothing else, so `fettle setup tools --all
  --global --deny` reported success and denied nothing, and an assistant
  whose own file tools stayed open kept using them out of habit.
  Registering makes Fettler available; only a deny makes it the route.
  `setup tools` now denies Read, Write, Edit, NotebookEdit, Grep, Glob,
  BashOutput and TaskOutput, and writes the tools paragraph into
  `CLAUDE.md`. At `--local` the denies are written. At `--global` they are
  offered until `--deny` is given, as guardrails always did. `setup
  guardrails` adds Bash, PowerShell and Monitor, because a declared task
  is what replaces a shell, and it adds the guardrails paragraph after the
  tools one. Re-running `setup tools` on a guarded project leaves the
  block alone. `--hooks` works at both levels.
- **Finding 2.8 belongs to the tools level, and the shells are finding
  2.20.** 2.8 reports a missing deny for the eight tools-level names and
  names `fettle setup tools CLIENT --local` as the remedy. 2.20 reports a
  missing shell deny, with guardrails on, and names `fettle setup
  guardrails CLIENT --local`. Both are judged across the client's global
  and project files together, so a deny in `~/.claude/settings.json` holds
  in every project.
- **VS Code Copilot was never routed to Fettler.** `setup` wrote a
  `permissions.deny` block into VS Code's `settings.json`, and VS Code has
  no such key. The block was ignored, Copilot kept its built-in read, edit
  and search, and `doctor` reported the project configured. VS Code has no
  deny list at all. What it has is the custom agent: a Markdown file whose
  `tools:` list says which tool sets the agent may use, and a set the list
  leaves out is one the agent cannot reach. `setup` now writes a Fettler
  agent file, described below, and never touches VS Code's settings.
  `doctor` judges the agent file, and a `permissions` block in VS Code's
  settings counts for nothing. The block an earlier `setup` wrote does no
  harm and can be removed.

## New

- **The Fettler agent file for VS Code Copilot.** `fettle setup tools
  vscode-copilot --local` writes `.github/agents/fettler.agent.md` in the
  project. `--global` writes it to the VS Code profile:
  `%APPDATA%\Code\User\prompts\fettler.agent.md` on Windows,
  `~/Library/Application Support/Code/User/prompts/fettler.agent.md` on
  macOS and `~/.config/Code/User/prompts/fettler.agent.md` on Linux. Its
  `tools:` list names the `fettler` server, the terminal (`execute`) and
  VS Code's own `vscode`, `agent`, `web` and `todo`, and leaves out `read`,
  `edit` and `search`. `setup guardrails vscode-copilot` takes `execute`
  out too and adds the guardrails paragraph, because a declared task is
  what replaces a shell. Running `setup tools` afterwards leaves the
  narrower file alone. The file binds when the Fettler agent is chosen in
  the chat; the default agent keeps every built-in tool. Because it adds a
  choice and changes nothing until chosen, the global copy is written
  without `--deny`. The project copy is a new governed file: fettle
  refuses to write it, like `.claude/settings.json`, so an assistant
  cannot put its own `read` and `edit` back.
- **Findings 2.8 and 2.20 read the agent file for VS Code.** 2.8 reports
  when VS Code is installed and no Fettler agent file leaves out `read`,
  `edit` and `search`, naming the project agent file and `fettle setup
  tools vscode-copilot --local` as the remedy. 2.20, with guardrails on,
  reports an agent file that keeps `execute`. An agent file with no
  `tools:` line gives the agent everything and clears nothing.
