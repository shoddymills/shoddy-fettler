# What 2.0.0 shipped

## Fixed

- A script field that names a file, `replaceFile`, `withFile` or
  `textFile` in an `edit` script, was read from anywhere on disk, with no
  check against the trees. Over MCP the script comes from a model, so a
  model could name any file on the machine, have its text spliced into a
  file in a tree, and read it back. That went past the read permission,
  the hidden scopes and the disclosure screen. The file is now a tree
  path, resolved through the boundary with `read` on both front ends. A
  path outside every tree is refused with exit `4` (`outside-root`), the
  batch does not run, and the refusal names the edit and the field.

## Breaking

- A glob holding `{`, `}`, `[` or `]`, or starting with `!`, is now
  refused with exit `2` (`invalid`), in `find`, `search`, `replace` and
  `--exclude`. It used to match those characters literally, so a brace
  alternation from another dialect matched nothing and said nothing. For
  an alternation, run two searches. For a bracket, put `?` or `*` in its
  place.
- A command-line script (`--script FILE`) whose `replaceFile`, `withFile`
  or `textFile` named a path relative to the current directory must now
  name a tree path: relative to the default tree, or written as
  `tree:path`. The script file itself is still read as your own file.

## New

- `roots` names the branch of a tree that is a checkout:
  `branch: main (local)`, or `detached at a1b2c3d (local)`. When the
  `.git` is above the tree, the next line names the repository folder.
  The line is local: it says what this machine has checked out, not what
  a remote holds. `--json` carries `branch`, `detached` and `repository`.
  Only `.git/HEAD` is read, plus the one `gitdir:` pointer a worktree or
  a submodule uses.
- `edit` and `batch` take a script from a file in a tree:
  `script_path` over MCP, `--script-path PATH` on the command line. A
  large script no longer has to travel inline as one large argument.
  Giving both `script` and `script_path` is refused.
- `read --numbered` (`numbered: true` over MCP) returns the text with each
  line as `N | text`, the form the terminal already prints. The hash is
  still the file's, and the prefix counts toward the 40,000-character cap.
- A `search` or `replace` whose glob matched no file says so:
  `0 files matched the glob; nothing was searched`. A `search` whose glob
  matched only files with no text says
  `N files matched the glob; none could be searched as text`. The `search`
  JSON answer gains `files_matched` beside `files_searched`.

# What 2.0.1 adds

## Breaking

- **The configuration file has three sections, one per level: `tools`,
  `guardrails` and `screenings`.** This applies to `.fettler.json`,
  `.fettler.local.json`, `.picker.json` and `.picker.local.json`. A file in
  the old flat shape is refused, and the message holds your own entries
  rewritten in the new shape, so the fix is to paste it. For fettle, before:

  ```json
  { "trees": { "work": { "path": ".", "screen": ["identifiers"] } },
    "tasks": { "build": { "run": "pwsh -File build.ps1" } },
    "models": "../models" }
  ```

  After:

  ```json
  { "guardrails": { "trees": { "work": { "path": "." } },
                    "tasks": { "build": { "run": "pwsh -File build.ps1" } } },
    "screenings": { "models": "../models", "screen": { "work": ["identifiers"] } } }
  ```

  A `screen` no longer sits inside a tree. It goes under `screenings`, keyed
  by the tree name, or the tree name, a slash and a scope path. For pick,
  `connect` goes under `tools.servers`, the databases under
  `guardrails.servers`, and `models` and `screen` under `screenings`, keyed
  by database or `database/scope-pattern`.
- **`setup` takes the level as its first word.**

  | Before | After |
  |---|---|
  | `fettle setup claude-code --local` | `fettle setup tools claude-code --local`, then `fettle setup guardrails claude-code --local` |
  | `fettle setup claude-code --global` | `fettle setup tools claude-code --global` |
  | `fettle setup claude-code --local --hooks` | `fettle setup guardrails claude-code --local --hooks` |

  `setup tools` registers the server and does nothing else. `setup
  guardrails` writes the deny list, the instruction block, the hook when
  asked, and a starter `guardrails` section. `setup screenings` checks
  burler and the models and writes a starter `screenings` section. The old
  spelling is refused and the message shows the new one.
- **`doctor --json` names a client's registration place `reach`, not
  `level`.** The values are still `global` and `repo`. The word `level` now
  means tools, guardrails or screenings, and each finding carries its
  `level`.

## Fixed

- **Finding 2.8 is judged the way the client merges its files.** A deny in
  `.claude/settings.json` binds whatever `.claude/settings.local.json` says,
  so a local file with no denies no longer raises 2.8. Before, `setup`
  wrote the denies to `settings.json` and reported nothing left to do, and
  `doctor` then reported 2.8 against `settings.local.json` and recommended
  the command just run. The finding now names `.claude/settings.json`, and
  running the remedy it gives clears it.
- **Finding 2.15 is retired.** fettle now opens the scratch folder itself,
  so the condition it reported no longer arises. Its number is not reused.

## Wider, on purpose

- **A folder with no configuration file now works.** It used to refuse.
  The folder fettle starts in is one tree called `work`, granted everything
  but execute, and a path that climbs out of it is refused as before. This
  is the one change that grants more than before. The launch folder is the
  narrowest tree there honestly is, a configuration file in a folder above
  it is still found and honoured, and a broken file is still a refusal.

## New

- **Three levels, named everywhere.** `roots` and `pick catalogs` open with
  one line per level, saying whether it is on and which file turned it on.
  `doctor` reports in a section per level and reports a finding only for a
  level that is on: a project without guardrails is not told it lacks a
  deny list. `help` opens with the levels that are on and groups the verbs
  by level. The MCP `instructions` say which levels are on for that launch.
- **fettle finds the client's folders itself.** At every level it opens
  this session's scratch folder as `scratch`, the client's `tool-results`
  folder read-only, and its `memory` folder read and write. Nobody declares
  them. Older sessions and the session transcripts stay outside. `roots`
  says how each folder was found. Declarations of these folders in an
  overlay can be removed.
- **Companion servers.** A registered MCP server whose registration passes
  `--root PATH`, such as sparky, has that folder opened as a tree named for
  the server, so fettle can write a file the companion reads in the same
  turn. With guardrails on, `doctor` reports a companion root inside a
  declared tree, inside a screened tree or scope, or in a folder a governed
  file switches, as the serious finding 2.19, and exits 2.
- **The machine file**, `%APPDATA%\fettler\fettler.json` on Windows and
  `~/.config/fettler/fettler.json` elsewhere. It holds facts about a
  machine, such as the models directory, under `tools` and `screenings`. A
  `guardrails` section in it is refused. It is a new governed file:
  fettle refuses to write it, like `.fettler.json`.
- **pick at the tools level.** A `.picker.json` with only a `tools` section
  is a connection and nothing else: every online database the login can
  enter is there, through the same query gate.
- **`serve` with no file at launch looks again on every call**, so a
  `guardrails` section written mid-session binds on the next call.

## Documentation

- **The site and the README now lead with the three levels.** The home
  page opens with why an assistant in 2026 is using command-line tools
  like it is 1976, a table that sets each denied built-in tool against
  `fettle` and says what went wrong, the arithmetic of one job, what the
  tools do, and a drawing of the levels. The README carries the same.
- **The pages read in the order the levels turn on:** Overview, Quick
  start, Tools, Guardrails, Screenings, Install, Reference. Each page opens
  with the level it describes. The tools page shows a search, a read, a
  stale edit and two refused writes as the terminal prints them. The quick
  start gains a third step that uses the tools. The screenings page opens
  with the four screens and the model each one needs. The reference is
  regrouped by level, with every anchor unchanged.
