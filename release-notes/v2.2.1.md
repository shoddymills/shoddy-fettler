## Fixed

- **A `read` with `from` past the end of a file answered empty text and
  said ok.** A read takes several paths and one `from`. A file shorter
  than that line came back with empty text, `truncated` false and no
  `next`, which is the shape of a complete read, and an assistant took
  the empty text for the file's content. A `from` past the end of any
  path in the call is now refused with exit 2 (`invalid`), naming the
  file and its line count. A `to` before `from` is refused the same way.
  It answered empty text with a `next` pointing back at `from`, so a
  caller following `next` with the same `to` never moved. A `from` of 0
  is refused, as `column` and `tail` already were. A `to` past the end
  still reads to the end. An empty file read from line 1 still answers
  empty text with `lines` 0.

## New

- **A path may carry its own range.** `read a.cs:634` starts at line 634,
  and `read a.cs:634-646` reads that range. This is the form of a search
  hit and a search `next`, so a hit passes straight to `read`, and two
  files in one call can start at different lines. A path with its own
  range cannot be combined with `--from`, `--to`, `--tail` or `--column`;
  the call is refused. A trailing colon and digits is always a range. On
  a POSIX filesystem, a file whose name ends that way is read by giving
  it a range: `notes:5:1` is the file `notes:5` from line 1.
- **`find` and `search` say what `limit` 0 means.** It means no limit,
  and the tool descriptions now say so.
